# The pre-spec step

For whoever writes the spec of a case's tests: the `/spec` session, started from this file, once the fill pass is merged. `<skill>` below is the folder this file sits in.

Before you write, read the case's tables, one `<case>/<slice>/oracle.jsonl` per slice, each holding the slice's rows and its declared-unplaced lines, and the case's row script (the program named by the `rows` command in `<case>/oracle.conf.json`). Where the user named a kind, read the kind file in full too: it says what shape the tests must be. The spec cites rows by id, and no expected value is restated or reworded in it. The spec is checked by `/spec`'s cold reader and built by `/go`, both unchanged, so everything below has to be in the spec itself.

## Decisions the spec must carry

Put these in the spec's Decisions, so `/go`'s builder and critic are held to them:

- **No row leaves through the spec.** There is no "out of scope", "parked", "later", or "covered elsewhere" for a row.
- **The spec carries a confirmation piece, after every test piece.** Its builder finds each row's test, claims that the test does what the row says, cites the test in `<slice>/test-fields.jsonl` — the claim's citation shows the test's name — writes an `Empty` record when no test exists, and runs `node <skill>/scripts/ledger.mjs check <case> test <slice>` before reporting. Its critic grades each claim against the honouring rule — a test honours the oracle only when the test, read in its file, asserts the row's expected value as the table holds it; a test that asserts what the code does at run time, or a weaker or different value, is refused — writes `<slice>/test-verdicts.jsonl`, and runs `node <skill>/scripts/ledger.mjs merge <case> test <slice>`, which appends CONFIRMED fields only. A confirmed claim names the red condition: what the code under test would have to do wrong for the test to fail.
- Expected values come from the row's written source, never from what the code does today.
- **The tests are graded against the table, not the code.** A test that asserts what the code does today, instead of its row's expected value as the table holds it, buys a green run with a wrong test: it is refused. The spec names the case's tables, one `<case>/<slice>/oracle.jsonl` per slice; review each test's assertion against its row's `Expected` there, and treat any disagreement as a finding, however green the run.
- Where a row is wrong, or the code contradicts it, the builder stops that test and says so in its report: never follow the code quietly, never reword or weaken a test to fit it.
- "They pass" is not the report. A builder's report lists every place the code and the row disagreed, and every assertion it could not make as the row states it, and why.
- A red-on-purpose test carries no skip and no expected-failure mark. It is left plainly red, because the table expects red for a row with a confirmed `Shortfall`, and the ledger reads the result.
- Tests in one file share no state.
- Write the test as the row says and let it fail. Do not change the test, the row, or the code; don't comment the red line out, move it, or change it.
- No workaround gets a test past a defect: no retry, no loosened match, and no input chosen to steer round the defect.
- **The naming rule.** A test names the row whose id equals the test's name, compared lower-case with only letters and digits: equality, not containment. The name is the id in snake_case, PascalCase, or camelCase, or the id verbatim. The ledger finds a row's test by that match and nothing else.
- **The confirmation piece's records.** The builder's claim in `<slice>/test-fields.jsonl` is `Id`, `Field` `Test`, `Value` the claim that the test does what the row says, and `Cites` naming the test file with a quote that shows the test's name; `Test` carries no `Source`. When no test exists, the builder writes an `Empty` record. The critic's verdict in `<slice>/test-verdicts.jsonl` is `Id`, `Field`, `Verdict` — one of CONFIRMED, PARTLY, WRONG, CAN'T TELL — `Evidence`, and `Judged`: the claim copied exactly, without its `Id` and `Field`.
- **The four verdict words, and what each means.** The critic grades each claim with one of them: **CONFIRMED**, the whole claim holds as it stands — the test, read in its file, does what the row says, and its citation names it — and only a CONFIRMED merges, closing the row on a `Ran` of the colour it expects; **PARTLY**, part of the claim holds and part does not, said exactly, with quotes; **WRONG**, the test does not do what the claim says, or asserts a weaker or different value than the row's; **CAN'T TELL**, part could not be checked, with what would settle it. Unsure between CONFIRMED and PARTLY, the critic writes PARTLY: a wrong PARTLY costs one round, and a wrong CONFIRMED closes a row whose test does not honour the table.
- **The Proof facts.** Each test piece's Proof is `node <skill>/scripts/ledger.mjs results <case> <the run's JUnit files> --slice <slice>`, never the test runner's own exit code: a runner exits non-zero when a red-on-purpose test fails. The confirmation piece's Proof, and the spec's Done means, are `node <skill>/scripts/ledger.mjs open <case>` exiting 0.
