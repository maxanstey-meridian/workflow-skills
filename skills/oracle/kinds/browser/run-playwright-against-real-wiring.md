## Run Playwright against real wiring

**Law:** Run Playwright against the real frontend, API, and database without `page.route` interception in end-to-end journeys, emitting JUnit XML through a dedicated oracle Playwright config (`playwright.oracle.config.*`, reused if one already exists) rather than altering the base config's reporter, placing specs under a case-scoped folder (`e2e/oracle/<case>/`), and keeping parallelism in Playwright config rather than per-file `test.describe.configure({ mode: "parallel" })` — when the base `playwright.config.*` already has a `fullyParallel: true` project for `e2e/oracle/**/*.spec.ts`, omit per-file parallelism boilerplate, and when it still runs `e2e/oracle/**` serially while `playwright.oracle.config.*` is parallel, flag or fix that once in the base config so `task ci` does not regress to serial.

**When:** Implementing or running any `browser` test suite.

Bad: Intercepting API responses with `page.route("**/api/forms", ...)` inside a browser journey test, adding `test.describe.configure({ mode: "parallel" })` to every spec file when `playwright.config.ts` already runs `e2e/oracle/**/*.spec.ts` with `fullyParallel: true`, leaving `e2e/oracle/**` serial in `playwright.config.ts` while `playwright.oracle.config.ts` is parallel, or placing specs directly in a flat `e2e/oracle/` folder.
Good: Running Playwright via `playwright.oracle.config.ts` against the live frontend, backend API, and database, with specs under `e2e/oracle/<case>/`, parallelism configured once in the base `playwright.config.ts` project for `e2e/oracle/**/*.spec.ts`, and JUnit XML passed to `ledger.mjs results`.
