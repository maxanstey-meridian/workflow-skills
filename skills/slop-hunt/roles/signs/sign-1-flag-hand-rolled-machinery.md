## Sign 1: Flag hand-rolled machinery

**Law:** Flag custom queues, outboxes, retries, timeouts, scheduling, locking, leases, caching, serialisation, standard-format parsing, identifier quoting, options validation, type mapping, reflection over metadata the framework already has, and dev tooling (diffing, comparison, and test harnesses), proving each against the nearest maintained replacement and its delta.

**When:** Evaluating custom machinery; name the nearest maintained replacement at the repo's framework and package versions (a framework feature, a library the repo already depends on, house doctrine furniture, or a new dependency; say which) and list the delta (each thing the custom code does that the replacement does not, whether a stated requirement in the repo's instructions, a spec, or a test pinning a user-facing need calls for it, and whether it could sit as a small extension on top). The custom code carries the burden of proof, so "no library does exactly this" starts the delta list rather than dismissing a lead; mark the finding `proven` when the replacement covers everything and `judgement` when arguing the delta is not worth its lines. A design that rules every library out (hand-written statements so a checker can see them, or a payload format no library reads) is a sign 13 finding priced at the machinery it forces. Do not flag the domain rules themselves (what a retention period means, or who may approve a case): product logic is the rules, not the machinery that carries them.

Bad: Dismissing a 200-line custom retry scheduler with "Polly does not survive app restarts, so no library does exactly this", or flagging a domain retention-period rule as hand-rolled machinery.
Good: Reporting the retry scheduler under sign 1 against Polly 8.4 (already referenced), listing the delta (backoff and jitter covered; restart survival uncovered and unrequested in specs, tests, or instructions), and leaving domain retention rules unflagged.
